# Batch 59 — encoded mixed chunk frame-loss repair

The prior raw-frame comparison did not detect an encoded MP4 issue. In all six real synthetic media cases on FFmpeg 7.1.5, the first seven-frame mixed chunk yielded only six decoded frames, and the existing production frame-count guard would reject it. Adding explicit 25 fps normalization after trim and setpts in mixed_chunks.filter_graph resolves the reproduced failure. The existing source FPS normalization, frame-index trim, end padding and original cumulative frame plan are preserved. Ordinary non-resume composition is unchanged. Because mixed renderer identity binds the helper source hash, previously saved mixed cache namespaces are retained but not selected automatically after this update.

New regression test tests/test_v4_real_mixed_chunks.py covers both mixed output variants and three aspect ratios, absent/present intro/outro, and non-frame-aligned sample offsets. It uses seven-frame chunks to exercise many boundaries in short synthetic clips, with actual libx264 encoding, exact frame count checks, cache save/restore and hash comparison, chronological concat and AAC mux from 16 kHz synthetic PCM, full video/audio decode, video duration within 1 ms of frame plan, audio duration within 30 ms of source sample count, sample-based SRT offsets, receipt reconstruction, input hash preservation and rejection of modified subtitles. No genuine speech or model output. These tests recreate the production encoder command sequence and invoke real production scene_plan, filter_graph, cache, card, decode, subtitle, receipt and audit helpers; they do not invoke the full compose entry point or exercise upstream approval/locking/stop orchestration.
